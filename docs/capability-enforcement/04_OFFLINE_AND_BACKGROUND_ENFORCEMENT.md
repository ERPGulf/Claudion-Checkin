# Offline and background enforcement

## Existing data integrity contract

`services/offline/AttendanceQueueService.js:submitAttendance` sends manual actions through the online-only branch. Only automatic actions can enter the offline queue. Automatic creation already required cached employee attendance configuration, appropriate location evidence and endpoint support. The settings administrator switch was mirrored asynchronously by `components/OfflineAttendanceBootstrap.jsx` into `offlineCapability.js`, leaving direct calls and changes during gate/timestamp awaits insufficiently protected.

New automatic attempts assert `attendance_action.auto_attendance` and current scoped employee mode 2 before execution. Offline admission also asserts `attendance_action.offline_attendance` before location evaluation and rechecks after asynchronous timestamp/configuration/provenance work. R4 adds a synchronous employee policy/auth-generation guard inside `enqueue`, after database preparation/deduplication and immediately before submitting a new INSERT. Accepted deduplicated rows remain recoverable. A disabled result uses the existing attendance `{allowed:false}` contract. No second capability store is added. The older administrator mirror remains for compatibility. A database write or HTTP request already submitted before policy reception cannot be recalled.

The confirmed tenant geo override now forms part of that existing AUTO capability: false/0/null denies new automatic actions regardless of employee mode 2. Final synchronous tenant and employee assertions run inside the INSERT callback after database/deduplication awaits, before online callbacks, native start/retention and after employee-policy awaits. Geo-only revocation stops both bootstraps' automatic monitoring when received, and pending background ENTER/EXIT receipts cannot become new punches. Scope, raw evidence and accepted attendance are preserved; the separate offline delivery endpoint does not acquire this new-admission veto. Manual attendance is unaffected solely by geo disablement.

## Pre-existing attendance after disablement

Disabling offline attendance prevents **new queue rows**. `OfflineAttendanceBootstrap` retains the existing drain-only behavior: `BackgroundSyncManager` continues delivery/recovery triggers while avoiding unnecessary employee-configuration refreshes. Already accepted attendance records remain delivery obligations, including legacy manual/photo records. Automatic feature disablement likewise does not invalidate previously accepted attendance. Nothing is automatically discarded, deleted, relabeled to another tenant or converted from unverified to successful.

Attendance attachment uploads are a separate, best-effort action. If `photo_upload` is disabled before an older queued record synchronizes, its attendance still delivers while a new photo upload is refused. The original queue payload retains its `photoUri`; this work does not delete it or claim that a failed attachment was uploaded. Existing attachment recovery does not automatically retry a photo after the attendance row has completed. Scope-verified outbox reconciliation may still read the shared history endpoint when attendance history UI is disabled; its internal `attendanceStatusRead` marker distinguishes positive-evidence recovery from feature history browsing.

`AttendanceSyncService.js:syncPendingAttendance` captures the authenticated employee, tenant, account and authentication generation. `AttendanceQueueRepository.js:claimNextPending` claims only the requested tenant/employee rows, preserving FIFO and atomic ownership. `AttendanceApi.js:pushCheckin` independently checks row ownership; `apiClient` rechecks the same scope before dispatch/retry. `attendanceQueueProvenance.js` reads current persisted identity and rejects tenant/account changes after awaits. Rows from a different tenant cannot upload under the active token even when employee codes match. Legacy rows with NULL provenance remain retained for review and are never assigned the current tenant by inference.

## Native capture and JavaScript authorization

Android `GeofenceBroadcastReceiver.kt` snapshots the registration's original owner and appends a durable event before emission. `GeofenceManager.kt:restoreFromStore` restores the stored fence after reboot/update. iOS `AutoAttendanceAppDelegateSubscriber.swift` primes Core Location before JS, and `GeofenceManager.swift:handleTransition` journals owner/configuration metadata; stale callbacks retain a capture issue rather than gaining current credentials. Neither native platform performs authenticated attendance requests.

No native source/API changes were needed. The JavaScript bridge's `startGeofence` and `retryInitialPresence` check tenant availability and current employee mode 1/2 before native dispatch and afterward. A denial or changed mode during native work stops that registration; eligible mode 1 is reconciled without automatic punches. The optional JS-only expected owner preserves auth generation; it is never sent as a native auth field. Existing native payloads/methods remain compatible with older binaries, and durable fields are passed only when supported.

Both bootstrap variants now observe tenant automatic availability. The durable bootstrap stops a revoked fence immediately, including while its serialized startup is awaiting configuration, and continues transferring native receipts to durable SQLite without creating new punches. The legacy bootstrap stops monitoring and prevents stale callbacks/replay from submitting. `utils/autoAttendanceRegistration.js` also checks capability before and after asynchronous office selection/registration. Employee modes 0/1/2 remain independent and unchanged.

Final-review correction: the earlier legacy path could replay an unowned historical record under a new employee's credentials. It now refuses actionable historical replay without capture-time ownership, retains the native record/processing mark, and binds fresh observed callbacks to their captured tenant/employee/generation. Existing expiration handling remains. A legacy binary has single-slot event storage, so retention is not a durable journal or guaranteed later automatic delivery; a subsequent native event can overwrite that slot. Accepted SQLite attendance rows remain unaffected. Controlled automatic staging should use the durable native APIs. R4 direct automatic/retry employee-mode enforcement is now fixed and covered by the regressions in [07](07-FINAL_GAP_ANALYSIS.md); DV-13 device evidence is still required.

`AutoAttendanceEventProcessor.js` checks automatic capability at receipt processing and at action execution. Denied receipts remain pending with a reason, and accepted outbox rows retain their original integrity/recovery rules. Warning-only receipts become handled evidence without punches. A native callback is never by itself authorization to create attendance. Native monitoring can continue under its last persisted configuration while JS is not running; it is stopped when a received denial reaches the running JS lifecycle. The app cannot claim instant server revocation or new policy knowledge while offline.

If a service or request guard returns an explicit local `FEATURE_DISABLED` or `EMPLOYEE_AUTO_ATTENDANCE_*` refusal after the receipt recorded dispatch intent, the existing known-no-insert callback clears that intent. The receipt remains pending instead of demanding server proof for an HTTP request never dispatched. Ambiguous transport outcomes continue to require positive server evidence; they are never treated as this local refusal.

## Known limits and validation

Feature settings refresh on session start, throttled foreground and manual retry. Same-scope geo/Boolean denials survive failed, omitted or malformed refreshes; missing fields retain compatibility separately from explicit null. No new expiry is invented. R4 employee reception remains scoped/ordered in the existing slice; caches seed only an absent matching answer. The six-hour cache threshold remains a refresh hint. Remaining backend questions concern geo 1/true/missing and cross-source manual exceptions; the disabled tenant geo override is closed. See `03-GEOTAGGING_AND_LOCATION_POLICY.md`.

The global endpoint-support cache and legacy administrator mirror remain older unscoped compatibility state cleared on auth cleanup. They can temporarily refuse admission until refreshed after unusual provisioning transitions; they cannot override an explicit scoped denial to grant queueing. A tenant-keyed support cache is a follow-up opportunity. Native/device delivery, reboot behavior and live backend acceptance require appropriate builds and staging; automated JS tests do not establish those results.
