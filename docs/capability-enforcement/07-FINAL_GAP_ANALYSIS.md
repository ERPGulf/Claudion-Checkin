# Final gap analysis

Reviewed 2026-10-16 against the checked-out implementation, all documents `00`–`06` and `FEATURE_MATRIX.md`, service callers, native sources and behavioral tests. The earlier 110-suite / 2,408-test result was the starting point, not proof of complete path coverage. No backend deployment/source, production credentials or device results were supplied.

**2026-10-21 contract follow-up:** backend-confirmed manual location combinations and explicit-null denial are now implemented and regression-tested. The existing geometry, feature slice, service, transport and session architecture remain. R1 is partially closed for individual tenant location semantics; cross-source location overrides and tenant geo precedence remain unresolved. R5 is partially closed for new explicit-null responses; missing/stale and ambiguous pre-upgrade caches remain compatibility limits. Current full-run results and release gates are in `09-RELEASE_READINESS.md`.

**Subsequent tenant geo confirmation:** false/0/null is now a mandatory automatic-attendance veto, even with employee mode 2. This closes that specific part of R1. The existing AUTO capability includes it at registration, replay, offline admission/final INSERT, service POST and 401 retry. Tenant geo 1/true/missing semantics and cross-source manual location overrides remain open; no additional precedence is invented.

**Conclusion:** confirmed client gaps, including R4 and the new location/null contract, were repaired without replacing the capability architecture. Controlled, non-production staging validation is appropriate under `09`. Production release remains blocked by the unresolved policy questions and missing backend/native/device evidence.

## Geo-tagging: verified scope and decision tables

Backend confirmation now resolves the tenant disabled case: [isFeatureEnabled](../../utils/featureSettings.js) and [central assertions](../../services/capabilityPolicy.js) veto AUTO when normalized tenant `geo_tagging_level` is 0. This overrides every employee mode without changing the employee enum. Historical P-11 remains relevant only to still-unconfirmed nonzero/unknown semantics and manual cross-source conflicts.

## Unknown, stale and revocation behavior

The compatibility table distinguishes wire null from missing fields. New explicit Boolean null is false; tenant geo false/0/null is canonical level 0 and vetoes AUTO. True/malformed/missing do not invent an enum level, and an omitted refresh cannot erase a prior geo denial. Tenant geo 1 semantics remain unresolved. Manual radius logic and ENTER/EXIT capture/deduplication are unchanged; the new gate controls authorization to turn evidence into attendance.

| Situation | Actual behavior | Optional feature may run without an explicit current allow? |
| --- | --- | --- |
| First login/no matching snapshot | `DEFAULT_WHEN_UNKNOWN=true` | Yes, for omitted/unfetched Boolean capabilities; backend authorization is essential |
| Settings unavailable before first success | Error/unavailable, no new snapshot; unknown compatibility remains | Yes |

Evidence: [normalization/merge/health/default](../../utils/featureSettings.js#L265), [slice scoping/request IDs](../../redux/Slices/FeatureSettingsSlice.js#L66), [refresh ownership](../../hooks/useFeatureSettings.js#L116), [bootstrap foreground refresh](../../components/FeatureSettingsBootstrap.jsx#L109), `capabilitySettingsLifecycle`, `capabilityPolicy`, `featureSettings`, `capabilityTransport` suites.

Distinguish three events: **server revocation** changes backend policy and requires independent backend authorization; **fetched-policy revocation** is a matching denial accepted by this app and blocks new client operations; **cached/offline behavior** follows the last known answer and cannot know a later server change. A cached true is not a current authorization lease. There is no defined expiration contract to “expire” it securely.

Safe changes made here close confirmed execution/ownership gaps while keeping existing compatibility. Future safe migration proposals require backend/product decisions: a versioned complete capability response, explicit supported missing-key behavior, a defined optional-feature authorization lease or unavailable-by-default policy for migrated tenants, and a documented recovery path. None should silently turn off essential manual attendance or weaken mandatory location policy.

The normalization fix is applied once at the raw `getFeatureSettings` response boundary. Normalized false is consumed by existing selectors, routes, direct services, raw attachment fetches, native callback checks and Axios retries. Entire malformed responses or null containers are still refused rather than inferring denials for every nested field. Regressions cover all Boolean paths, a null-only recognized response, prior true, failed/partial/malformed refresh, JSON cold hydration, old/new request order, tenant switching, direct reads/mutations/uploads, photo/break and final upload/401 checks. Location regressions cover all four tenant combinations inside/outside radius, mandatory employee conflicts, GPS/clock failures, policy and geometry changes during awaits, direct Axios, retry ownership and accepted success. Ordered `employeeLocationPolicy` metadata in the existing slice closes the final employee-storage-read race, handles location-only responses without changing mode, survives hydration and prevents rejected incomplete mobile policy from relaxing a mandatory rule. See `featureSettings`, `capabilitySettingsLifecycle`, `capabilityNullContract.integration`, `manualTenantLocation`, `manualLocationTransport`, `manualEmployeePolicyRace`, `manualAttendanceScope` and `capabilityAttendanceHook` suites.

## Validation and remaining limits

Final checks for this review are recorded in `09-RELEASE_READINESS.md`; the earlier `05` result remains historical. Native/device cases are all **NOT RUN** in `08-DEVICE_VALIDATION_CHECKLIST.md`. Backend authorization, live settings/employee response shapes, SDK-refresh compatibility, photo association and background/reboot behavior still require a disposable staging setup.

Existing best-effort photo association remains a separate HIGH risk: `AttendanceCamera`/`attendancePhotoUpload` pass FormData containing `custom_image` and a check-in docname, while [putUserFile](../../services/api/upload.service.js#L57) serializes its first argument as `employee_code` and does not use that docname. No backend contract establishes a safe replacement, so this was not rewritten. Attendance remains accepted even if attachment fails; original queued photo URIs are retained, but completed-row attachment retry is not implemented.

Remaining logging of employee/location/backend data elsewhere is a privacy follow-up; this review removed the demonstrated expense Axios credential leak, without claiming a whole-app logging audit. `employee_shift`, `offline_attendance_version`, salary/trip capability mapping, legacy endpoint-support cache scoping and open Jest handles retain the limitations in the release issue table.
