# Capability enforcement audit

Follow-up review: [07-FINAL_GAP_ANALYSIS.md](07-FINAL_GAP_ANALYSIS.md) records additional confirmed gaps and targeted fixes; [09-RELEASE_READINESS.md](09-RELEASE_READINESS.md) is the current release verdict. Stage A/B and provenance statements below describe the earlier task.

## Stage A — baseline, before production changes

Inspected on 2026-10-16. This section records the pre-change findings; the numbered companion documents describe the implementation and remaining limits. No production code was changed before this audit was recorded.

The settings API was **not enforced throughout the app**. Existing architecture is worth retaining: `services/api/featureSettings.service.js:getFeatureSettings` is the only settings endpoint wrapper; `utils/featureSettings.js` normalizes the response; the persisted `FeatureSettingsSlice`, shared hooks and `withFeatureGate` drive menus and route mounts. `FeatureSettingsBootstrap` refreshes on login and on foreground after 30 minutes, with manual retry. This is reception-based revocation, not instant server revocation.

### Confirmed enforcement and gaps

- Loan, leave, expense, complaints, resignation, records, attendance requests/history and automatic attendance have route mappings. `navigation/app-navigator.jsx` wraps mapped modern/legacy screens with `withFeatureGate`, which prevents mounting and responds to live settings. Both Home grids and modern shortcuts filter settings. Legacy saved pins and the legacy picker do not.
- Every feature-specific API service can be invoked directly without checking settings. `apiClient` guards authentication and attendance queue scope, but no feature. Its 401 retries can send operations after a capability changes. Four raw attachment fetch paths bypass that client. Shared `get_attendance_details` also supplies essential current attendance status: a blanket endpoint ban would break check-in/out reconciliation.
- Attendance break and photo flags mostly control presentation. `useAttendanceAction` still fetches/ends breaks when disabled. The camera route and camera submission/upload functions are unguarded. `photo_upload` applies to attendance photos; general HR attachments belong to their owning feature.
- `selectFeatureSettings` returns an unscoped snapshot despite its comment; scoped selectors exist but are not used by normal consumers. `pendingScope` does not reject late responses. The refresh hook captures a scope separately from the service's auth read. A malformed successful response normalizes to all unknown and can erase an explicit denial.
- Offline queueing already checks the administrator mirror and endpoint support. The established rule is to stop **new** queueing when disabled while continuing delivery of existing attendance. The effect-populated mirror leaves direct callers and policy-change races to examine. Current `attendanceQueueProvenance`, queue migration and upload scope checks already bind records to tenant/employee and preserve unowned legacy records; stale prose describing employee-only isolation is not current code.
- Automatic runtime authorization uses employee `get_employee_data.geotagging`, user opt-in, scoped configuration and durable event provenance. Tenant `auto_attendance=false` currently only hides the screen; both bootstrap variants and direct automatic APIs ignore it. Native Android/iOS code records and emits location events; JavaScript, not native event success, authorizes submission.
- Existing enum evidence (`AutoAttendanceSlice`, labels, normalizer tests) is **0 disabled, 1 monitoring/warnings only with no punches, 2 monitoring and automatic IN/OUT**. `geo_tagging` from settings is parsed but unused. `docs/auto-attendance-sdk/07-OPEN_QUESTIONS.md` P-11 explicitly leaves its precedence against employee `geotagging` unresolved. Likewise settings restriction switches versus per-employee policy are not a documented replacement contract. Do not invent precedence or relax employee restrictions.
- `employee_shift` has no implemented shift screen, service or shift-aware automatic behavior. Salary advances and trips have no corresponding settings key. Their capability contract needs backend clarification.

### Stage B plan based on confirmed evidence

Strengthen the existing slice/selectors and fetch lifecycle; preserve known settings on failed/malformed refresh, ignore obsolete responses, and expose explicit snapshot health. Add one service/request policy boundary sourced from that same Redux snapshot, including retries and raw uploads. Repair legacy entries, camera and break paths. Apply tenant automatic/offline denials at execution boundaries and monitoring lifecycle, retaining queued attendance and current tenant provenance. Keep established unknown-field compatibility explicit and retain mandatory employee location policy. Add behavioral regressions, run focused and full Jest suites, and report unavailable lint/type/native/live-backend checks honestly.

### Backend and fixture limits

Only the example payload in the task attachment was supplied; named Rowad/TDI payloads were not attached. Tests must use synthetic representative enabled/disabled configurations and cannot claim those names identify verified production configurations. Backend source and live staging responses are absent. Client gates are defense in depth; backend authorization remains mandatory and unverified.

## Stage B — implemented result

1. **Was the settings API enforced everywhere?** No. The baseline above identified presentation-only checks and unguarded execution. The existing authority has now been extended at confirmed boundaries; unresolved geo/location and missing feature contracts remain explicit blockers to a blanket claim.
2. **Which features were only hidden?** HR/document features, attendance requests/history and automatic attendance had menu/route guards but no service enforcement; photo/break enforcement was mostly presentation. Legacy shortcut filtering also had gaps.
3. **What could execute while disabled?** Direct HR reads/mutations/uploads, camera submissions, break callbacks/timers, automatic attendance and stale retries; offline admission could use a delayed mirror/earlier policy. Confirmed paths now recheck current scoped capability.
4. **Are API operations centrally guarded?** Yes for discovered optional feature operations: shared service assertions plus exact transport mapping on requests/retries, ownership checks on delayed responses and explicit raw-upload checks. Essential shared status/clock/profile/totals and accepted-record delivery keep their established purposes.
5. **Is offline attendance controlled?** New automatic queue admission checks current offline and automatic availability at the boundary and after awaits. Manual punches remain online-only. Previous accepted attendance still drains for its original tenant/employee; no records are deleted or relabeled.
6. **Are geo and geofencing independent?** Existing employee modes 0/1/2 remain distinct from manual restriction/checkout exceptions and offline admission. Explicit tenant automatic disablement now stops new automatic actions/monitoring. Tenant geo/location versus employee-policy precedence is still unresolved and was not invented.
7. **Can stale settings or tenant state bypass?** Foreign snapshots, obsolete responses, delayed cross-tenant results, logout suspension and received denials during retries/admission are now checked. Same-scope stale restrictions persist. Unknown/first-session settings still use documented legacy compatibility, and unseen remote changes cannot be enforced instantly.
8. **What changed?** Scoped selectors/refresh ownership/health/partial merge; centralized service and transport guards; camera/legacy shortcuts/break callbacks; automatic registration/receipt processing and offline admission checks; regression tests and all requested documentation. No new feature store/dependency, auth rewrite, API payload change or native source change.
9. **What passed/failed?** The final complete Jest suite passes; lint is blocked by missing repository configuration, and no configured TypeScript project exists. Exact commands/results and intermediate failures are in `05-TEST_RESULTS.md`.
10. **What remains unverified?** Overlapping backend policy semantics, shift/version/trip/salary capability contracts, backend authorization/live tenant acceptance and native/device behavior. Details and migration constraints are in `06-REMAINING_RISKS.md`.

All changes remain local and uncommitted. The requested `FEATURE_MATRIX.md` path links to the complete numbered matrix, avoiding divergent copies.
