The current native debug app ran on disposable API35 Google Play ARM64 `emulator-5560`, package `com.bazim.claudioncheckin`, version1.2.1/code24/targetSDK36. This was not Expo Go. Synthetic QR provisioning supplied ordinary storage/Redux provisioning; actual Login UI authenticated against the isolated localhost mock. No attendance session, queue row, native event or backend attendance record was seeded. Only real app attendance POST handlers created records. Test data survived upgrades/restarts.

The fresh Google Play image initially had no fused location cache. Opening Maps, skipping account sign-in and requesting current location initialized GPS. `adb emu geo fix LONG LAT` then delivered real OS fixes with accuracy5m. A host-invoked ordinary Expo Location watch kept the provider active; it creates no attendance events. Weak/uncertain fixes used Android's shell test GPS provider, with OS authorization unchanged. This is controlled native location injection on the actual app, not evidence of physical indoor reception.

All policy responses came from actual authenticated requests, not fabricated Redux authorization. Host-only manual helper uses `performManualAttendanceTransition` and `userCheckIn`, with real location/policy checks and no direct session writes; these were service-level integration calls, not automated UI taps. The temporary employee restriction change was restored, and tenant location restriction stayed active. Failed manual attempts with inaccurate cached location created no records (`48`/`51` responses). Successful manual intervention used a real95m-from-center fix with accuracy20m: ordinary manual radius checks permitted it while strict recovery remained uncertain.

The accepted/disconnected case has one JS autoCheckInOut log and two HTTP requests. A lower-level transparent retry is consistent with this evidence, but its origin was not positively instrumented. The existing app must rely on backend atomic duplicate prevention. Mock dedup is not evidence that the real staging/Frappe endpoint is idempotent.

Screenshots `23-permission-onboarding-en.png` and `24-permission-onboarding-ar.png` show the existing onboarding modal, not the recovery notice. Screenshots26 show the actual EN/AR weak-GPS notice. Waiting screenshots28 were separately captured. Do not infer synchronized checkout from a queued label.

NOT TESTED on this actual emulator: invalid coordinate delivery, access API exceptions, generic geofence error injection, exact floating-point boundary equality, late cancelled callback against a newer attempt, logout/tenant/employee handoff during interruption, every crash instruction boundary, queue refusal,30s server-response timeout, unknown-origin sessions. Native/Jest deterministic coverage is separate. Natural permission restarts, offline restart, repeated service toggles, retired native callbacks and repeated initial callbacks were exercised.

Physical indoor reception, OEM battery behavior, fully unobserved off/on cycles, terminated-app delivery guarantees and real Frappe staging persistence remain untested. Release requires staging verification of original timestamp preservation and atomic duplicate prevention for same employee/original timestamp/type.
