## Defect found and retested

The original iOS recovery used `requestLocation()` and immediately finished on its first cached result. Actual retry under simulated updates returned in 9 ms, rejected the stale fix, and repeatedly left recovery pending. The request now uses one dedicated `startUpdatingLocation()` attempt bounded to 15 seconds, ignores stale/invalid/uncertain observations until decisive fresh proof, and stops on proof/error/timeout/cancellation. The attempt-token and monotonic-deadline checks remain. The current binary was rebuilt and installed without clearing its sandbox. The original loss/generation survived, outside recovery then passed, and both later inside recoveries passed through the actual native → SQLite → attendance pipeline. No region-capability or accuracy guard was bypassed.

## Other runtime and coverage limits

- Initial iPhone 18 Pro/iOS 27.0 (24A434) app genuinely ran and authenticated, but Core Location returned `isMonitoringAvailable(for: CLCircularRegion.self)=false`; the app correctly refused registration. A standalone read-only native probe in both booted runtimes confirmed iOS27 false versus iOS26.5 true. **BLOCKED** for geofence attendance on iOS27; the primary tests therefore ran on iOS26.5. See [iOS27 capability](ios27-corelocation-capability.json), [iOS26 capability](ios26-corelocation-capability.json). This probe is diagnostic, not evidence of an attendance transition.
- Real iOS27 permission reads were also exercised: Always/full accuracy → available; denied → foreground loss; When In Use → background loss; Always restoration → available. No AUTO session existed in that diagnostic sandbox. See `access-initial.json`, `access-always-revoked.json`, `access-when-in-use.json`, `access-restored.json`.
- **NOT TESTED as actual simulator cases:** ±200 m accuracy, malformed/negative/missing coordinate accuracy, exact boundary equalities, deliberate late provider callbacks, a measured 15-second no-response timeout, battery saver, access-read API exceptions, generic geofence errors, all manual/UNKNOWN-origin and tenant/employee/mode/geometry matrices, queue refusal, ambiguous accepted-response faults, every crash transfer boundary, a real installed SQLite schema upgrade, and terminated-app automatic relaunch. These must not be inferred from the passes above.
- Two actual concurrent retry API calls with no simulated fixes both returned pending within 7 ms, so they do **not** establish a measured timeout; an existing request or immediate native provider error can produce this result. See [actual retry output](no-fix-concurrent-retry.json). Deterministic attempt ownership/deadline/late-token and geometry/journal behavior are separately covered by the Foundation harness: [99 passing checks](native-foundation-tests.log). That harness does not prove Core Location delivery.
- Physical indoor reception, reduced-accuracy behavior on physical iPhones, real suspension/termination/relaunch, system wake timing, battery behavior, and entirely unobserved access off/on cycles remain **NOT TESTED**. The actual precision UI change was first observed on foreground, and its event was not backdated to the UI tap.
- The unsigned simulator Debug app logged the existing Expo Notifications keychain entitlement error `-34018`. It did not prevent attendance, but APNs/local-notification delivery was not validated. The visible development warning is recorded in screenshots; it is not an attendance status. See [diagnostic](initial-startup-diagnostics.log).
- Live staging/Frappe timestamp preservation remains **UNVERIFIED**. Only the isolated mock's actual accepted OUT record was read back. No production requests or data changes were made.
