## Employee configuration and location rules

`fetchEmployeeData(employeeCode)` reads tenant/token at request time, performs employee-data GET, and returns `data.message`. `getOfficeLocation` independently fetches the same contract and writes legacy `photo`, `restrict_location`, `unrestricted_checkout_location`, `employee_locations`, and `geotagging`. Mobile contexts must have explicit complete attendance flags, and restricted employees must have usable locations/radii. QR normalization retains legacy defaults. The configuration cache also records employee ID/docname and tenant key. [employee.service.js:10](../../services/api/employee.service.js#L10), [getOfficeLocation:92](../../services/api/attendance.service.js#L92), [cache policy validation:59](../../services/offline/attendanceConfigCache.js#L59).

Authoritative location scoring prefers GeoJSON first-feature coordinates, interpreted longitude/latitude, then flat coordinates. Distances use `getPreciseDistance`; within-radius is positive radius and distance <= radius. Selection is the **nearest center**, not any matching office and not a union of office regions. One fence is registered for the chosen office. iOS clamps radius to its supported maximum; Android passes the positive radius through. Bootstrap substitutes 100 when the chosen radius is nonpositive. [attendanceLocations.js:30](../../utils/attendanceLocations.js#L30), [attendanceLocations.js:77](../../utils/attendanceLocations.js#L77), [attendanceLocations.js:110](../../utils/attendanceLocations.js#L110), [bootstrap:466](../../components/AutoAttendanceBootstrap.jsx#L466), [Swift manager:165](../../modules/expo-auto-attendance/ios/GeofenceManager.swift#L165).

`autoAttendance.parseLocationCoords` is a display helper with flat-first priority; it is not identical to authoritative GeoJSON-first scoring. `resolveOfficeName` chooses the nearest cached office to a fence center without a maximum-distance condition, so a display name does not prove registration belongs to the current policy. [autoAttendance.js:53](../../utils/autoAttendance.js#L53), [autoAttendance.js:77](../../utils/autoAttendance.js#L77).

Automatic online requests trust the native transition and do not re-enforce radius, require a photo, or request fresh GPS. Their coordinates identify the office center, not the employee's measured position at crossing. Automatic cached-policy queueing disables radius enforcement and tolerates no GPS fix. Manual restricted punches enforce office location; unrestricted checkout uses its own rules. [autoCheckInOut:473](../../services/api/attendance.service.js#L473), [offline gate:207](../../services/offline/offlineAttendanceGate.js#L207), [userCheckIn:247](../../services/api/attendance.service.js#L247).

## Session decision and idempotency rules

The durable record contains status, origin, start/end times, and closing origin. IN is allowed only when closed; OUT only when open. Either manual or automatic origin may close an existing open session. Failed submission leaves state unchanged. A queued allowed result commits local state but sets `serverConfirmed: false`; Redux mirrors the resulting state. API execution is serialized under the process-local session lock. [session state:62](../../utils/attendanceSessionState.js#L62), [session state:198](../../utils/attendanceSessionState.js#L198), [session state:259](../../utils/attendanceSessionState.js#L259).

Server reconciliation uses the request-issued timestamp to avoid overriding a newer local start and uses the legacy last-checkout floor to avoid stale reopen. `resolveActiveSessionStart` accepts known status time fields, stored start, and Redux start, rejecting values at/below checkout or >60 seconds into the future; it selects the maximum valid candidate. Native live events do not undergo this same time filter. [session reconciliation:335](../../utils/attendanceSessionState.js#L335), [attendanceSession.js:89](../../utils/attendanceSession.js#L89), [bootstrap:355](../../components/AutoAttendanceBootstrap.jsx#L355).

There is no end-to-end exactly-once guarantee. Current protections are the session lock/state skip, replay timestamp mark, SQLite unique index, ordered atomic claims, strict upload result interpretation, and exact duplicate verification. Server transaction behavior and idempotency are not established by these client mechanisms. [geofenceEventLog.js:52](../../utils/geofenceEventLog.js#L52), [database:159](../../services/offline/AttendanceDatabase.js#L159), [verification:32](../../services/offline/AttendanceVerification.js#L32).

## Time semantics

Native event time is local callback-receipt epoch milliseconds. `resolveServerTimestampAt` gets current server time and subtracts the event's age measured from a device `nowMs` taken before the time request. Invalid/nonpositive age falls back to current server time. It emits second-precision naive wall-clock text; this is not a timezone-qualified ISO instant. [auto timestamp:72](../../services/api/attendance.service.js#L72), [Android receiver:57](../../modules/expo-auto-attendance/android/src/main/java/expo/modules/autoattendance/GeofenceBroadcastReceiver.kt#L57), [Swift transition:227](../../modules/expo-auto-attendance/ios/GeofenceManager.swift#L227).

Queued timestamps use `formatOfflineTimestamp` with a device-global cached server-clock offset; absent offset defaults zero. Offset capture compares server wall-clock parsed in device-local time with request-start device epoch, without RTT midpoint correction. The offset is not tenant-specific and cleanup does not remove it. Device clock/timezone changes, request latency, DST, and server formatting are material unknowns for chronological replay and exact verification. Second precision also collapses same-action events within one second under the SQL dedupe key. [serverClock.js:24](../../utils/serverClock.js#L24), [serverClock.js:65](../../utils/serverClock.js#L65), [serverClock.js:111](../../utils/serverClock.js#L111), [database:159](../../services/offline/AttendanceDatabase.js#L159).

## Authentication, errors, and logging

`apiClient` reads current tenant/tokens for ordinary requests. A queue `attendanceSyncScope` additionally asserts persisted identity/auth generation and pins the tenant URL/auth header. Ordinary 401 gets one refresh/retry with shared refresh coordination; ordinary 403 passes through. Refresh-terminal failure invokes cleanup/logout; transient refresh failure preserves the session. `x-skip-auth` provisioning is retained. [apiClient:485](../../services/api/apiClient.js#L485), [apiClient:518](../../services/api/apiClient.js#L518), [apiClient:335](../../services/api/apiClient.js#L335).

Automatic online calls are ordinary requests and do not pass queue scope. A delayed callback can capture an old employee but later read a newer tenant/token; generation protection is materially stronger on the queued drain. Effect cleanup alone does not undo a request already dispatched. This is a **POTENTIAL RISK**, not a demonstrated cross-tenant server write. [bootstrap:233](../../components/AutoAttendanceBootstrap.jsx#L233), [auto service:452](../../services/api/attendance.service.js#L452).

Attendance error classification is message-first: duplicate, missing endpoint, auth, configuration, then narrowly recognized validation. Unrecognized server/local errors remain recoverable blocked; 5xx and recognized transport failures are pending; 401/403 without recognizable text are auth-blocked. Automatic online failure is queued only when `shouldQueueFailure` approves, cached policy exists, admin allows queueing, and endpoint is not known unsupported. Manual failures are not queued. [attendanceErrors.js:181](../../services/offline/attendanceErrors.js#L181), [attendanceErrors.js:224](../../services/offline/attendanceErrors.js#L224), [queue service:178](../../services/offline/AttendanceQueueService.js#L178).

Current logging includes raw employee responses/location arrays, automatic punch payloads, refresh-form request data, and generic transport bodies/responses. Therefore credential/PII-safe logging cannot be claimed for the whole attendance/auth path. This report describes logging sites without reproducing their contents. Expected attendance refusals are generally logged; programming errors also report nonfatal crash information. [office service:119](../../services/api/attendance.service.js#L119), [auto service:481](../../services/api/attendance.service.js#L481), [apiClient:72](../../services/api/apiClient.js#L72), [apiClient:406](../../services/api/apiClient.js#L406), [auto service:504](../../services/api/attendance.service.js#L504).
