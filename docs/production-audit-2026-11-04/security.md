# Security and privacy assessment

## Confirmed remediation

QR login and geofence diagnostics emitted raw error/event payloads; Home emitted private topic names; offline diagnostics could serialize employee/location/server fields. Both presentation variants now use bounded metadata, counts or redaction. Regression fixtures contain synthetic credentials and locations only. HR/camera error diagnostics received the same treatment without altering API error shapes or confirmed attendance outcomes.

Final review also removed arbitrary development feature-settings response/error fields and the direct-attendance catch's raw refresh body. Three additional regressions prove those private values stay out of diagnostics and a confirmed manual IN remains committed after a totals-refresh failure. This does not claim that every third-party/native diagnostic or future arbitrary Error is automatically sanitized.

QR publication and FCM setup/callbacks now reject superseded authentication generations. Queue history, counts and recovery rows now accept captured tenant/employee ownership; known foreign-tenant rows do not appear under a repeated employee code. Legacy NULL-provenance evidence remains unchanged and conservative. See [auth/push](auth-network-security.md), [geofence/UI](geofencing.md) and [offline](offline.md) for reproductions, files and tests.

`firebase.json` had debug Crashlytics collection enabled, contrary to the service/architecture's documented release-only default. It is now false; release automatic collection and JavaScript error-handler chaining remain true. Installed RNFirebase 24 native code checks that debug flag before collecting. The change requires a native rebuild; an OTA alone does not modify an installed binary's Firebase configuration. Native configuration tests guard this policy.

## Remaining protection gaps

- **Credentials and employee data:** access/refresh tokens use AsyncStorage; access tokens also enter persisted Redux. SQLite attendance data has no application-level encryption. These confirmed protection gaps remain; the migration design below is not implemented and does not establish encryption or recovery guarantees.
- **Public build variables:** the lookup configuration uses `EXPO_PUBLIC_*`; public bundle configuration cannot serve as a confidential server-side security boundary. No environment values were printed, copied into fixtures or submitted externally. Keep backend authorization/rate limits independent of embedded configuration.
- **Error surfaces:** several HR service contracts still expose raw backend message text to UI; a blanket change would alter validation feedback/localization. Plan endpoint-specific app-owned mapping while preserving result shapes. Arbitrary Error messages/stack passed to crash reporting remain a caller-owned privacy boundary.
- **Permissions:** camera, location, background location, notifications, microphone and motion declarations were inspected. Permission purpose copy/OS privacy labels and actual use need a release review on each store/device; this audit did not remove declarations that native dependencies may still require.
- **Build assets:** the scoped tracked filename check found no `.p12`, `.p8`, `.jks`, `.keystore`, `.pem`, `.key` or `.env*` file. Public Firebase configuration is present. This filename check is not a forensic secret-history scan or proof that every artifact/log is sanitized.
- **TLS and backend contracts:** mobile typed addresses enforce HTTPS and SDK transport rejects redirects/cookies. Legacy provisioned schemes remain compatible by design; changing them requires a provisioning migration. No certificate validation bypass was added and no real backend security test was attempted.

No employee, credential or location data was uploaded, and no production attendance call or new monitoring integration was introduced. `npm audit` sent dependency metadata to npm's registry. Crashlytics already exists; collection controls and privacy-safe diagnostic ownership need to remain part of release review.

## Credential and attendance storage migration design — not implemented

This is a proposed platform/security change requiring approval, native capability delivery and physical-device recovery evidence. No credential key, Redux schema, database file, backup setting or native journal was migrated or removed in Phase 2. [React Native's security guide](https://reactnative.dev/docs/security) confirms AsyncStorage is not encrypted and distinguishes secure credential storage from persisted Redux. That supports addressing the current gap; it does not make a particular migration safe automatically.

### Credential authority and compatibility

1. Introduce a lazily loaded credential-store adapter behind the existing **sole writer `saveTokens`** and request-time readers. Persist access/refresh as one validated secure-store envelope with schema version, tenant/employee/account binding and credential revision; never advance memory before its authoritative durable write. Preserve authentication-generation checks and the serialized logout/write boundary. Do not persist OTPs/passwords or move attendance rows into a keychain item.
2. Ship a native capability build and matching runtime first. Old binaries receiving JS must retain the current guarded legacy implementation. A native module missing or a protected store temporarily locked must not crash startup, clear provisioning or invoke the mobile SDK on a background launch.
3. During a declared compatibility phase, **legacy storage remains authoritative**, with a verified secure mirror. Mirror failure retains the working legacy credentials and marks migration incomplete. Do not prefer a stale secure mirror: an old binary/rolled-back bundle may have rotated the legacy refresh token after the mirror was written. This phase improves migration preparedness but does not close plaintext exposure.
4. Cut over only after an approved minimum binary/runtime and rollback floor exclude writers that understand only legacy credentials. Secure storage then becomes authoritative; writes must durably save/read back the complete token pair before memory/login publication. Remove the persisted Redux token through a versioned state migration only after secure recovery is verified. Legacy credential deletion and eventual mirror removal require separate approved cleanup, not a silent first-launch operation.
5. Logout invalidates the generation first, serializes removal in both stores and prevents a delayed refresh/migration from restoring a session. It retains provisioning needed for QR sign-in and every queued punch/journal receipt. A credential-store failure is a storage outcome, not a server rejection of the refresh token.

### Locked devices, reinstall and backup

Represent secure reads as **available / absent / temporarily locked / failed**, not a single nullable token. Before first unlock after reboot, suspend authenticated uploads and retain native events for later owned ingestion; do not rehydrate a failed read as signed out or overwrite stored session state. After unlock, resume normal scoped recovery without an automatic login/OTP flow.

Choose Keychain accessibility and Android key protection explicitly with platform ownership. Expo documents first-unlock accessibility for background use, Android encrypted preferences and backup/key-loss behavior; biometric-bound authentication can invalidate data after enrollment changes. A background attendance token must not require an interactive biometric prompt. Device-only/backup policy needs native review; the Expo wrapper labels its device-only first-unlock constant deprecated, so do not adopt it merely from the name. [SecureStore platform behavior](https://docs.expo.dev/versions/latest/sdk/securestore/).

Bind secure credentials to an installation identifier and tenant/employee identity. Handle iOS items surviving reinstall without silently restoring a previous installation's session. Exclude nonportable encrypted credentials from Android backup; restoring ciphertext without its key must lead to a recoverable sign-in state while retaining attendance evidence. An old-binary rollback after secure-only cutover is unsupported unless a separately reviewed recovery mechanism exists; do not restore plaintext automatically to make it work.

### Database and journal protection

Evaluate supported encrypted SQLite and protected native-journal storage as a coordinated **new native build**. A key held only in JS memory or unavailable before first unlock must never cause a journal reset or make a native callback discard evidence. Retention, OS file protection and backup policy cover SQLite WAL/SHM files, native journals and photos as well as the main database. Avoid adding continuous location work to compensate for locked storage.

A future migration should use an isolated encrypted copy under an interprocess-safe writer exclusion mechanism, preserve the original read-only until verification, and compare integrity, row count, IDs and all attendance evidence. Preserve v6 claims/dispatch markers, pairing/source IDs, review/rejected/resolved/cancelled states, NULL tenant provenance, timestamps and legacy payloads. Atomically publish a recoverable migration manifest only after handles/checkpoints and durability are accounted for. If writer exclusion across native/headless/UI runtimes cannot be guaranteed, do not perform the cutover. Retaining plaintext rollback copies also retains exposure, so their later removal is a separate approved release operation.

### Required validation before implementation approval

| Fault or compatibility boundary | Required outcome |
| --- | --- |
| Crash before/after secure write, readback, revision or cutover marker | Deterministic authority; no mixed token pair or accepted mirror claimed as authoritative. |
| Server rotates refresh token; secure write or compatibility mirror fails | Current durable authority remains explicit; no memory-first token update or blind retry of an uncertain mutation. |
| Old binary/old OTA writes legacy tokens during compatibility | Legacy remains authoritative; a stale secure mirror cannot replace the newly rotated pair. |
| Missing native module / malformed secure envelope / wrong tenant binding | Guarded legacy mode before cutover, explicit recovery after cutover; no credential or queued-row reassignment. |
| Background boot before first unlock, then unlock with pending native events | No session reset, SDK begin, token deletion or event acknowledgment without durable ownership; recovery resumes afterward. |
| Logout/account switch while a migration/read/refresh is pending | New generation wins; no old credential write or attendance adoption. |
| Biometric change, key invalidation, reinstall and restored backup without key | Honest recoverable auth state; preserve evidence, never silently recreate/reset the queue. |
| Database copy, WAL/checkpoint or manifest interrupted at each boundary | Original recoverable; no record loss, duplicate admission or simultaneous writers. |
| Rollback before and after secure-only cutover | Tested supported pre-cutover recovery; explicit release-floor restriction afterward. |

Run deterministic storage fault tests on synthetic fixtures, then reboot/first-unlock/locked-device/reinstall/backup tests on signed Android and iOS devices. Verify QR/mobile sign-in, SDK refresh compatibility and delayed offline recovery on disposable staging employees. These are **planned closure tests**, not passing results from this task. Closure owner: mobile platform + security + release engineering, with an approved threat model, native capability/rollback design and evidence that both credentials and attendance survive the complete matrix.
