# Attendance

## Attendance domain logic
[utils/attendanceSession.js](../../utils/attendanceSession.js) is pure, well-tested logic for resolving the active check-in session start time from noisy inputs (server status, persisted AsyncStorage time, Redux time) — it normalizes unix-seconds vs ms, rejects future/pre-checkout timestamps, and is the basis for the session timer.

[utils/attendanceSessionState.js](../../utils/attendanceSessionState.js) is the durable `CHECKED_OUT ⇄ CHECKED_IN` state machine that **both** entry points drive — the manual screens and the geofence listeners. Every check-in/out goes through `performSessionTransition({ type, origin, execute })`, which refuses illegal moves (so duplicate check-ins/check-outs never reach the backend), serializes concurrent attempts, and commits only after `execute` returns `{ allowed: true }`, which can mean online acceptance or a durably queued automatic punch. The transition result distinguishes `queued` from `serverConfirmed`. Because the record stores the session `origin` (`MANUAL`/`AUTO`/`UNKNOWN`), a geofence EXIT closes whatever session is open — this is what makes manual check-in → automatic check-out work — and is a no-op after a manual check-out. The record lives in AsyncStorage (`attendanceSessionState`), not Redux, because the listeners run after an OS background relaunch; Redux mirrors it (`attendance.sessionOrigin`) for the UI. `reconcileSessionFromServer()` re-aligns it with `resolveActiveSessionStart()` on screen mount/focus.

The OS delivers ENTER/EXIT to native code even when the app is killed, but the attendance call needs JS. Native receivers append every crossing to a durable journal (`GeofenceStore` / `GeofenceEventJournal`); JS copies it into SQLite (`ingestPendingNativeEvents` → `AutoAttendanceEventRepository`) before acknowledging the native copy, then drains it through `performSessionTransition`. Binaries without the journal (`supportsDurableEvents()` false) fall back to the legacy bootstrap, which replays only the last native transition (`getLastEvent()`) at launch, gated by the high-water mark in [utils/geofenceEventLog.js](../../utils/geofenceEventLog.js) and capped at `MAX_REPLAY_AGE_MS`. Replayed logs are **backdated** to the real crossing: `autoCheckInOut({ occurredAt })` → `resolveServerTimestampAt()` subtracts the event's device-measured age from the server's wall clock, so device/server clock skew cannot shift the logged time. Location-restricted check-in ([attendance.service.js](../../services/api/attendance.service.js) `getOfficeLocation`/`userCheckIn`) uses `geolib` distance against `employee_locations`, gated by `restrict_location` / `unrestricted_checkout_location` flags cached in AsyncStorage.

**Background delivery differs by platform** ([docs/android-background-attendance.md](../android-background-attendance.md)). On Android, every durable capture, boot/package replacement and JS queue admission (`requestQueueDrain` → `scheduleBackgroundSync`) asks [AttendanceSyncScheduler](../../modules/expo-auto-attendance/android/src/main/java/expo/modules/autoattendance/AttendanceSyncScheduler.kt) for a WorkManager pass. A pass requires a network with INTERNET capability, not VALIDATED. `AttendanceSyncWorker` starts the shared ReactHost with no Activity and runs the `ClaudionAttendanceSync` headless task ([AndroidAttendanceBackgroundTask.js](../../services/offline/AndroidAttendanceBackgroundTask.js)) through the same processors, so nothing needs the app opened. Scheduling is coalesced: a pass that has not started absorbs new requests, a running pass gets one appended follow-up, and passes never overlap. **A pass never returns `Result.retry()`**: WorkManager keeps appended work `BLOCKED` until its parent succeeds, so a backed-off pass made a new crossing wait (3 min 52 s on the emulator; WorkManager's cap is 5 h). Leftover work instead arms the separate `claudion-attendance-sync-retry` timer (30 s up to 15 min, cancelled once nothing is left), which never starts JS, so replacing it cannot cancel an upload. "Leftover" is `hasBackgroundSyncWork` / `hasBackgroundEventWork`, which exclude terminal, manual-review and `endpoint-missing` rows; the latter are kept and still attempted by any pass. iOS has no worker: a crossing relaunches the app into `AttendanceBackgroundRuntime` (about 25 s of background time), so an online crossing uploads then, but a punch queued offline waits for the next JS run (next crossing, FCM push, or app open). Neither platform promises timing: Doze, App Standby buckets, OEM battery managers (Samsung Sleeping apps) and force-stop delay or suppress work, and nothing recovers a crossing the OS never delivered. The worker is native code: a new build, not an OTA.

**Automatic attendance is employer-controlled.** `selectAutoAttendanceConfigured` is the only on/off: `employee_checkin_setting` must send the tenant switch `attendance_action.geo_tagging: true` AND the account's scoped employee `geotagging` (from `get_employee_data`) must be 2, the only mode that is monitored and checks in and out. Mode 1 (warnings-only) is never monitored, never punches and is never asked for location: no warning behaviour is defined for it. The app's earlier mode-1 monitoring only produced the screen's technical reliability banners, the backend ignores the mode, and manual attendance never reads it, so mode 1 awaits a backend definition. Crossings captured under an older mode-1 registration are still recorded as handled, never as attendance. Only the boolean `true` enables: `false`, `null`, a missing field, the retired numeric levels and strings are all off, and `auto_attendance` is no longer read, so a value cached by an older build is inert. Mode 0 is never monitored or prompted for location. A refresh never carries `geo_tagging` over: an answer that omits it is off, while a failed request keeps the last answer. There is no employee switch; the Automatic Attendance screen shows a read-only status. Persisted answers for the same account are the last established configuration, so monitoring restores on relaunch and background launches. [FeatureSettingsBootstrap](../../components/FeatureSettingsBootstrap.jsx) refreshes them at sign-in, on a stale foreground, and on reconnect when the last answer failed or is stale. Operational state is separate: the registering bootstrap publishes `autoAttendance.monitoring` (`active` / `unavailable` / `permission`), and `describeAutoAttendanceStatus` combines it with the configuration and a live OS permission read into Disabled by administrator / Location permission required / Initializing monitoring / Active / Monitoring unavailable. The manual screen promises an automatic check-out only once monitoring is `active` for a mode-2 employee. Location access (foreground, background, precise) is read from the OS every time and requested through one shared flow, `askForLocationAccess` in [utils/autoAttendance.js](../../utils/autoAttendance.js). Its explanation is the full-screen [LocationAccessExplainer](../../components/AutoAttendance/LocationAccessExplainer.jsx), registered with the flow and kept up behind the system prompts it starts: Continue only on iOS (Apple's pre-alert rule), Continue or Not now on Android, where Back means Not now. [AutoAttendanceOnboarding](../../components/AutoAttendanceOnboarding.jsx) runs the flow after sign-in only on settings and employee policy received for the account since launch, only in the foreground, never when access is granted or can no longer be requested, and once per account (`locationOnboarding`; a verified ineligible answer forgets it). The screen's "Grant location access" retries it and offers Settings when the system will no longer ask. See [docs/features/geotagging-permission-onboarding.md](../features/geotagging-permission-onboarding.md). A forced sign-out stops the geofence, so crossings after it go unrecorded until sign-in; captured receipts and queued punches are retained.
