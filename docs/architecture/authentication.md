# Authentication

## Authentication & onboarding (QR or mobile → tokens)

QR and mobile sign-in are presented at equal weight: both Welcome variants share the [SignInOptions](../../components/Welcome/SignInOptions.jsx) cards, and both password Login variants offer QR rescan and mobile as matching alternatives below Login. Do not demote either to a text link. [MobileLogin.jsx](../../screens/MobileLogin.jsx) is one themed auth shell shared by both UI preferences; focused mobile/account, OTP, password sign-in, and password creation steps remain under the unchanged `"mobile login"` route. [selectIsLoggedIn](../../redux/Slices/AuthSlice.js) remains the authority for swapping navigators: neither method navigates to the authenticated app after success.

**QR/password remains the established path.** A QR scan stores tenant, employee, and attendance-policy keys, including `baseUrl`, `api_key`, and `app_key`, and records `auth_method: "qr"`. It dispatches the employee identity and navigates to `"login"`. Login calls [generateToken](../../services/api/auth.service.js) with `{ api_key, app_key, api_secret: password }` → `employee_app.gauth.generate_token_secure`. The existing generation guard and `saveTokens()` persist access/refresh tokens; Login writes `employee_id` and dispatches `setSignIn`. [useLogin](../../hooks/useLogin.js) is unchanged, and the legacy Login still owns its existing inline implementation.

**Mobile discovery and credentials live in [useMobileLogin](../../hooks/useMobileLogin.js).** A stored `backendUrl` skips lookup and its configuration entirely. Otherwise, normalize and validate the company code with `@erpgulf/server-lookup`, then call `lookupServer` once with literal `process.env.EXPO_PUBLIC_SERVER_LOOKUP_URL`, `EXPO_PUBLIC_SERVER_LOOKUP_SECRET`, and `EXPO_PUBLIC_SERVER_LOOKUP_ALPHABET` property accesses at the lookup call site. Configuration is validated lazily; there is no retry or lookup cache. Instead of a company code, the employee can switch to a typed server address: it is normalized and validated with the package's `normalizeBackendUrl`/`validateBackendUrl`, refused at the field unless HTTPS, reduced to its origin, and used without lookup or its configuration. Transport and backend-shape failures on that path name the address rather than the setup service. Keep the company code in screen memory only. Persist the resolved `backendUrl` only after SDK `begin()` succeeds. “Change company” clears this preference and form state, cancels stale operations, and serializes preference removal after pending writes. It leaves canonical session `baseUrl` and QR provisioning intact.

[mobileAuth.service.js](../../services/api/mobileAuth.service.js) reuses one `@erpgulf/auth-sdk` client per HTTPS origin. SDK calls go through the service's `expo/fetch` transport, because React Native's global fetch ignores the SDK's `redirect: "error"`; it also omits cookies and sends no-store, and is required lazily so the module stays safe to load at startup. Call methods through the client object because they depend on private fields. Render the SDK's `credentials` requirements (`required`, `optional`, `disabled`) and password purpose; hide disabled fields and omit blank credentials from `complete()`. A password with purpose `create` needs a confirmation, at least 8 characters, and not only spaces. Request an OTP when a new flow needs it, and use manual Resend for subsequent attempts, including after an unconfirmed request; the cooldown is 45 seconds, or `expiresIn` when shorter. Create/reset password actions require the SDK's capabilities, are offered only on `SIGN_IN`, and reset is never offered on `ENTER_PASSWORD_AND_OTP`. They call `setPasswordWithOtp`, then begin a new flow — also when the outcome is unconfirmed (non-retryable timeout, network, 5xx or invalid response); setting a password alone does not sign in. Rejected OTP/password fields are cleared. [AUTH_CAFM_GAP_ANALYSIS.md](../../AUTH_CAFM_GAP_ANALYSIS.md) records where this flow deliberately differs from the CAFM reference. Handle SDK errors through `isAuthError`, `code`, and `retryable`; never show SDK messages. Release builds log only `{ code, httpStatus, retryable }`. Development builds (`__DEV__`) log SDK URLs, statuses, timing, request IDs, and policy metadata under `[auth-sdk]`. `[mobile-auth]` traces operations and hand-off stages, including normalized identifiers and identity match/rejection reasons; `handoff.failed` names the failing stage. The isolated debug logger omits credentials, tokens, authorization headers, raw payloads, and free-text errors/stacks. These console diagnostics never write credentials to storage or change authentication semantics. No SDK cold-boot flow or launch-time `begin({ sessionActive: true })` is used, preserving background geofence relaunch.

**Mobile steps preserve the original SDK flow and its credential contract.** Sign-up captures OTP first, then opens a separate password screen when the SDK requires or permits a new password. Optional sign-up has a visible **Skip for now** secondary action, which calls `complete(flow, { otp })` and leaves managed-password generation to the SDK; mandatory sign-up has no Skip. The SDK has no independent OTP-verification API: the temporary code is verified only during final sign-up or `setPasswordWithOtp`, so intermediate navigation must not claim server verification. Password creation/reset never asks for the code again. Password-and-OTP sign-in captures password first, then OTP, and submits both together. Optional/Optional sign-in remains SDK-determined: employees with a user-known password get password sign-in; those without one get OTP, with only separate capability-based create/reset actions. Do not offer credentials the resolved flow disables or mutate the flow to invent an alternative. Back navigation preserves the flow and resend cooldown without sending another code. Final OTP errors return to the OTP step. Cancel, company/mobile changes, authentication reset, and successful completion clear transient credentials; raw OTP/password values never enter persistent storage. See [docs/mobile-sign-in.md](../mobile-sign-in.md#focused-authentication-steps) for the screen sequence.

**Mobile hand-off must validate identity and attendance before publishing login.** `completeMobileSignIn` invalidates the auth generation before SDK completion and rejects missing refresh tokens or stale results before writes. It fetches the authenticated employee profile using normalized SDK `employee.id`, falling back to the existing SDK policy `employeeId` only if the result ID is absent. Matching SDK `id` and fetched `name` verify identity without an attendance code; a canonical mismatch rejects before fallback. Conflicting document aliases (`name` / `employee`) or attendance codes (`employee_code` / `employee_field_value`) reject. Explicit attendance codes are preserved; otherwise a canonical match supplies the verified docname as the app employee identifier. Fallback retains docname + explicit-code checks against SDK `id` or, if absent, SDK-validated policy `employeeId`. SDK `name`, fetched `employee_name` / `first_name`, and phone numbers never prove identity; names are used only for display. Tenant attendance endpoints still need live validation with docnames when codes are absent. Explicit `restrict_location`, `unrestricted_checkout_location`, and `photo` flags are required; restricted employees also need a usable reporting location with a positive radius.

After validation, hand-off snapshots affected provisioning/policy/session keys, removes QR credentials and stale policy, persists both URLs plus employee identity and `auth_method: "mobile"`, and saves tokens exclusively through `saveTokens(..., generation)`. It awaits the scoped attendance cache and legacy policy mirrors before identity actions and `setSignIn`, then runs the unread-count fetch and success toast. A persistence failure clears failed credentials and restores prior provisioning only while its generation remains current; cleanup must not overwrite a newer session. Queued attendance is retained. A tenant change clears the prior tenant's durable session; same-tenant ownership remains governed by `applySessionOwner`. Successful mobile sign-in clears `api_key`, `app_key`, stale `company`, and the previous Redux username, so employees rescan to use QR again. Later mobile policy refreshes reject incomplete responses, and a missing restriction mirror refuses manual attendance.

**Secure random values gate mobile availability.** [App.js](../../App.js) installs [mobileAuthCrypto](../../utils/mobileAuthCrypto.js) before auth navigation mounts. The helper requires native `expo-crypto` inside `try/catch`, probes `getRandomValues`, and installs it only when needed. Older binaries without that capability retain QR sign-in; mobile links and route registration are hidden. `expo-crypto` requires a new native build and matching runtime/version fields; OTA alone cannot add it. Both ERPGulf packages ship ESM and are mapped/transformed in [jest.config.js](../../jest.config.js).

**Live staging remains unverified.** Synthetic SDK transport tests, Metro exports, native builds, and simulator smoke checks do not establish the live employee-field mapping or whether `employee_app.gauth.create_refresh_token` accepts SDK-issued refresh tokens. Validate QR, mobile/password, and OTP-only sign-in with disposable staging employees before rollout. Refresh incompatibility blocks rollout; do not add a second refresh path. See [docs/mobile-sign-in.md](../mobile-sign-in.md) for the remaining checks and environment setup.

## Testing

[serverLookup.test.js](../../__tests__/serverLookup.test.js) decodes synthetic sealed tokens with Expo's own UTF-8 decoder, and [mobileAuthCrypto.test.js](../../__tests__/mobileAuthCrypto.test.js) checks native capability fallback. Route selection is pinned in [authProvisioning.test.jsx](../../__tests__/authProvisioning.test.jsx); [mobileLoginUi.test.jsx](../../__tests__/mobileLoginUi.test.jsx), [loginUi.test.jsx](../../__tests__/loginUi.test.jsx), and [qrScanUi.test.jsx](../../__tests__/qrScanUi.test.jsx) preserve presentation and QR behavior. Keep fixtures obviously fake and report live staging separately from local validation.
